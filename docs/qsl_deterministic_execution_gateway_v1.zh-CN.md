# QSL 确定性执行网关 V1：设计契约

> 状态：`P0_RECONCILE_ONLY_GATE_IMPLEMENTED_NOT_WIRED`
>
> 本文不启用任何账户、券商、paper、shadow、live、订单或资金动作，也不为 P4–P6 赋予范围或完成状态。

## 为什么需要单独的网关

预授权策略验签通过，只能说明“一个外部根签过的、短期的、精确 bundle 的许可链存在”。它不能自己限制仓位、损失、订单频率或券商的未知结果。

P0 现已实现 [`reconcile_only_admission_gate.py`](../python/scripts/reconcile_only_admission_gate.py)：它支持 OpenSSH SSHSIG 与 Cloud KMS P-256 两种外部根；在签名 policy、精确风险摘要、精确 target 和有效期全部匹配时，最多给出 `RECONCILE_ONLY`；否则给出结构化 `PARKED`。该程序不读取账户、不连接券商、不执行对账，也没有订单接口。

所以未来的自动系统必须分成三层：

```text
AI / driver（研究、监测、证据）
        │ 只写候选与证据，不能调用券商
        ▼
策略根 + autonomous_policy_gate（验签、时间、bundle、target）
        │ 只给出 allow / PARKED，不能提交订单
        ▼
确定性执行网关（风险限额、幂等、对账、熔断）
        │ 唯一持有受限券商身份
        ▼
券商 API
```

网页策略切换控制台、GitHub Actions、主控会话、driver 和 LLM 都处于前两层之前，不能成为券商写入路径。它们可以请求重新评估，但不能绕过网关或重置熔断。

## 网关的唯一接受条件

未来网关在任何可能改变账户状态的请求前，必须同时验证：

1. 当前时钟、连接和最近一次对账均健康；任一不可得即 `PARKED`。
2. `autonomous_policy_gate` 成功，且其 `QSL_TRUSTED_POLICY_ROOT_SHA256` 由网关自身受控的部署配置注入，而非由请求、workflow input 或仓库文件提供。
3. policy 中的精确 deployment bundle、target、stage 和 `risk_control` 摘要与网关加载的不可变版本一致。
4. 请求带有网关生成的幂等键；相同键只能得到同一已记录结果，未知券商结果不得盲目重试。
5. 每项确定性风险限制均在本次操作**之前**通过：单笔、总敞口、策略敞口、日内损失、频率、交易时段、允许标的与账户状态。
6. 熔断未触发；若触发，默认只允许记录和对账，不允许新增风险。任何减仓/平仓规则也必须预先编码，不能由 AI 临场决定。

“策略已签名”“CI 全绿”“回测有效”“AI 建议下单”都不在这个列表中，单独出现时一律不足以放行。

## 最小接口与状态

网关 V1 的 P0 准入接口只支持两个结果：

| 结果 | 含义 | 后续动作 |
| --- | --- | --- |
| `PARKED` | 任一输入缺失、过期、不一致、未知或超过限制。 | 拒绝新增风险，写入最小审计事件，等待确定性条件恢复。 |
| `RECONCILE_ONLY` | 没有资格产生新风险，但允许读取并核对已有状态。 | 不创建、修改或重复提交订单。 |

在独立的纸面/影子证据证明之前，不定义 `ORDER_ACCEPTED`。这避免“先把接口做成能下单，再补风控”的倒置。`RECONCILE_ONLY` 只是未来独立只读服务可消费的许可；它本身不会执行读取。

## 身份与数据边界

- 只有网关进程可读取券商凭证；AI、CI、网页、策略代码、policy 文件和审计日志均不可读取。
- policy 签名私钥不进入本仓、不进入 CI、不进入网关运行账户；网关只读取公开的根、签名 policy 与受控的根哈希。
- 原始市场数据、账户数据和审计索引分开保存；审计事件只保留必要的哈希、时间、结果、原因码和版本，不复制凭证或订单 payload。
- 网关服务身份应只拥有完成其单一工作所需的权限；策略根签发身份、网关凭证身份与 AI 研究身份必须不同。

## 自动化如何仍然无人值守

无人值守不是取消边界，而是让边界由预先配置的确定性服务持续执行：AI 可以自动发现异常、产生候选、运行证据和提出 release evaluation；策略根可按其固定规则签发或续期**不扩大范围**的策略；网关仍只接收精确、验签、未过期且满足风险上限的输入。

若要扩大 stage、账户、bundle、风险上限、可交易标的或 AI 权限，必须生成新的策略与风险版本，并由策略根的独立规则处理；AI 不能在运行中修改自身的边界。

## 接入顺序

1. 在独立于 AI/CI 的控制位置准备 public trusted root，并把其 SHA-256 固定到未来网关的部署配置。若选择 GCP KMS，root 必须钉住一个 `EC_SIGN_P256_SHA256` 的具体 key version 和它的 PEM 公钥，而不是让运行时自行选择 KMS key。
2. 为一个**不产生订单**的目标签发短期 policy，验证 gate 能给出可审计结果。
3. 接入只读对账，验证断网、时钟偏差、数据/策略不一致和重复幂等键都默认为 `PARKED`。
4. 仅当上述证据完整时，再为纸面或影子执行提出新的、可复核的任务定义。

第 1 步的公开 Cloud KMS root 已在 6 个 Quant GCP 项目初始化，并逐把读取核验；记录见 [GCP P0 控制根部署 V1](qsl_gcp_p0_control_root_deployment_v1.zh-CN.md)。但其 SHA-256 尚未注入任何网关部署配置，步骤 2–3 也未在任何真实服务安装。本设计和 P0 准入代码都不能被作为部署、交易或 promotion 许可。
